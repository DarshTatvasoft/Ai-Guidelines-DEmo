Core rule  C O R E R U L E  Work by stage, not by tool feature: Understand / Explore → Plan → Implement → Check / Review.   Use  what your tool provides for each stage (section 3), and move on only when the stage's check is done.  Understand and Plan do not change code.   Debug only when something fails , not after every change.   Every  change is reviewed, built, and tested by the developer   before it is committed.  Typical flow.   A human check closes every stage. Explore   / Understand  •   Use it to explore   available options,   unfamiliar code, ask questions and compare approaches.   It does not  change code.  •   Give precise context: select the code, or reference files and folders with the tool's file - mention syntax.  •   Check:   confirm the AI's explanation matches the code and the requirement. Correct any wrong assumption  before you plan.  •   Do not use it as a development workflow. Every message re - sends the whole chat, so long Q&A chats cost  more time and tokens. Move on to Plan, then Implement.  •   Verify API details in official docs before you rely on them.  5. Plan  •   Use Plan for   normal and complex   tasks; simple tasks can skip it.  •   Give the requirement, constraints, and acceptance criteria up front, and answer the tool's clarifying  questions.  •   Review the plan for: files to change, order of steps, edge cases, validation, tests, and data migration or  rollback where relevant.  •   Check:   a human approves the plan   before   any code changes; for complex work, the tech lead approves.  Update the plan first if scope changes.  6. Implement and Check / Review  •   Implement   only the approved plan , in small steps. If scope changes, stop and update the plan first.  •   Read each step's diff before the next step. Do not accept large changes you have not read.  •   Use automatic edit approval only for low - risk work, never for security, authentication, production data or  infrastructure changes.  •   Check / Review:   review the full diff, build, run tests, and go through code review as usual. Fixes go back to  Implement.  7. Debug  •   Use it only when something fails:   a build or test failure, an exception, wrong behaviour or a reported bug. It  is not a step after every change.  •   Start with evidence: repro steps or issue link, expected vs. actual behaviour, and   paste the exact error  message, stack trace or log lines   as they appear, not a description from memory.  •   Prefer a   targeted fix at the failure point   over broad refactoring, add a regression test, and remove  temporary logging and breakpoints before committing. Then go back to Check / Review.  •   Debug against local or test data. Use production data only when the Company/Client has approved it, and  mask sensitive values.

Common rules across all stages  Rule   What it means  One task per chat   Start a new chat for each task. Long, mixed chats lose context and cost more tokens.  Project instructions   Keep project conventions in the tool's instruction file ( CLAUDE.md , Cursor rules,  .github/copilot - instructions.md ,   AGENTS.md ,   GEMINI.md ) so every stage follows  them.  Model choice   Model Selection Standard: select the lowest suitable model explicitly (not Auto);  stronger for complex or critical work.  Developer owns the  code  Review every suggestion and diff. Build, run tests, and go through code review as  usual.  Data safety   Never   paste secrets, credentials, production, or restricted data into chat. Use only  Company/Client - approved accounts and tools.  Human approval   Mandatory   for security, authentication/authorization, production data, infrastructure,  and other high - impact changes.  9. Copy/paste prompt examples  Stage   Prompt  Understand /  Explore  Explain how duplicate customers are detected in CustomerImportService, and which methods  would need to change to match on email instead of customer code. Do not change any code.  Plan   Plan CSV customer import using the existing API/service pattern. Inspect the existing Customer  and import code first. List the files to change, the order of steps, edge cases, and the tests to  add. Ask me if anything is unclear.  Implement   Implement step 1 of the approved plan only. Follow the existing code style and do not change  anything outside the plan. Then stop, show me the diff and run the tests.  Debug   Customer CSV import fails for files over 10,000 rows. Expected: the import completes and  reports failed rows. Actual: it stops after about 30 seconds with this error:  System.TimeoutException: The operation has timed out.  at CustomerImportService.ImportAsync(Stream file) in ImportService.cs:line 87  Reproduce it, find the root cause, and propose a targeted fix. Do not refactor unrelated code.
