TatvaSoft   AI Development Tools Guidelines   TVS - DEV - AI - GL - 01 | v1.0 | 25.09.2026  TVS · Internal   Page   4   of   16  Guidelines at a Glance  The ten rules below summarise this document. Every team member using AI development tools is expected to  follow them.  01  Prompt precisely  State goal, context, scope, constraints and expected outcome. No vague prompts  like "Fix this".  Prompting  02  One task per chat  Start a fresh chat when switching tasks. Reference files   —   don't paste whole  codebases.  Context Engineering  03  Make every repo AI - ready  Project instruction file (AGENTS.md / CLAUDE.md), named AI champion, sandbox  branch, CI/PR review checks.  Mandatory Usage  04   Configure tools at project level  Start with restrictive permissions; use skills, agents, hooks and MCP deliberately.   Tool Setup  05  Use the lowest model that works  Escalate to a stronger model only for complex, risky or critical work. Select models  explicitly.  Model Selection  06  Explore   → Plan → Implement → Check / Review  A human check closes every stage. Understand and Plan are read - only. Debug only  when something fails.  Plan, Ask & Debug  07  Least privilege for MCP  Read - only where possible, approved servers only, confirm the target before any  write action.  MCP  08  Never share secrets or sensitive data  No credentials, client data, PII or production data in AI tools. Company - approved  accounts only.  Data Privacy  09  Humans own the output  All AI output is reviewed, built and tested before commit, merge or release. It is  never trusted by default.  Data Privacy  10   Report exposure immediately  Accidental data exposure must be reported at once   —   never concealed or delayed.   Data Privacy  P R E C E D E NC E  Where client - specific, contractual, regulatory, privacy, security or licensing requirements are   stricter   than  these guidelines, the stricter requirement always applies.

TatvaSoft   AI Development Tools Guidelines   TVS - DEV - AI - GL - 01 | v1.0 | 25.09.2026  TVS · Internal   Page   6   of   16  Prompting Guidelines   —   Do's & Don'ts  K E Y T AK E AW A Y  A good prompt clearly states the   goal, relevant context, scope, constraints and expected outcome   —   and  asks for the minimum change needed.  ✔   DO  ✔   Explain the   goal, context, scope, constraints   and  expected outcome .  ✔   Specify which files/modules   may change , what  must   stay untouched , and whether API, database  or dependency changes are allowed.  ✔   Include business rules, current vs. expected  behaviour, errors or logs where needed.  ✔   For complex or unfamiliar tasks, ask the AI to  inspect the existing implementation first .  ✔   Break large tasks into   smaller steps   with clear  acceptance criteria .  ✔   Review AI changes: only intended files modified,  existing behaviour preserved, edge cases and error  handling covered.  ✘   DON'T  ✘   Use vague prompts such as   "Fix this" ,   "Make it  better"   or   "Optimize this" .  ✘   Allow unrelated refactoring or unnecessary  rewrites   —   ask for the   minimum required change .  ✘   Reference irrelevant files   —   keep prompts  focused.  ✘   Continue in the same chat when moving to a  different task   —   start a new chat .  ✘   Include confidential information:   API keys,  passwords, connection strings or PII . Why it matters  Long conversations, failed attempts, unrelated code or excessive file content make the AI   lose focus   and  increase the chance of   incorrect changes .  ✔   DO  ✔   Start a   fresh chat   when switching tasks or when  debugging becomes cluttered.  ✔   Reference files directly   instead of repeatedly  pasting their contents.  ✔   Keep stable project rules in   persistent instruction  files   or workspace settings.  ✔   Document architectural and business decisions   in  the repository .  ✔   Give AI agents   clear boundaries   on what they can  modify.  ✘   DON'T  ✘   Carry failed approaches forward into new  attempts.  ✘   Dump large parts of the codebase into the  prompt.  ✘   Rely on chat history as the project's   source of  truth .  Detailed reference:   Context Engineering

TatvaSoft   AI Development Tools Guidelines   TVS - DEV - AI - GL - 01 | v1.0 | 25.09.2026  TVS · Internal   Page   11   of   16  AI Model Selection  G O L D E N R U L E  Use the   lowest model tier that can handle the task reliably . Move to a stronger model only for higher  complexity, uncertainty, security concerns, architectural decisions, production data, infrastructure or other  high - impact changes.  Select the model explicitly   —   automatic selection may pick a more capable and more expensive model  than the task needs.  Choose by task level  Task level   Typical work   Recommended approach  Simple   Small, well - defined changes following  an existing pattern.  Lower - tier approved model.  Normal   Feature work across several files or  layers within the existing architecture.  Standard development model; create a plan  before implementation where appropriate.  Testing and review ideally require higher  model but if not possible then same model will  work  Complex / Critical   Cross - cutting design, authentication /  authorisation, production data,  infrastructure, migrations,  performance - sensitive work.  Stronger approved model + additional review +  fresh context + mandatory human approval  before merge or deployment.  Testing / Code  Review  Verifying and reviewing the  implementation.  Same or stronger model as development. For  normal and complex work, use a separate  agent or fresh context so the review is  independent.  Cost & safety  •   Reserve stronger models for work that genuinely needs them.  •   Use   scripts or automation   for repetitive, deterministic activities where practical.  •   Never give secrets, production credentials or restricted information to an AI tool unless the Company or  Client has   explicitly approved   that environment.  Detailed reference:   AI   Model   Selection

Model Context Protocol (MCP)   —   Integration & Safe Usage  K E Y T AK E AW A Y  MCP lets AI tools connect to   approved   external systems. Always apply the   principle of least privilege .  What MCP is & why use it  A standard way for AI development tools to retrieve project information or perform supported actions through  connected services   —   such as   Figma, Jira, documentation systems   or other internal tools.  Less context switching   Better project context for the AI   Automates repetitive work via  natural language  ✔   DO  ✔   Grant   only the permissions required   for the task.  ✔   Use   read - only access   where possible.  ✔   Prefer   development / test credentials   over  sensitive production accounts.  ✔   Use MCP servers from   trusted and approved  sources only.  ✔   Review permissions when a server is   installed or  updated .  ✔   Disable or remove   connections no longer  required.  ✘   DON'T  ✘   Enable unnecessary   edit, delete or administrative  capabilities.  ✘   Place API keys, tokens, passwords or other  credentials in   source code , commit them to   Git , or  paste them into   AI conversations .  ✘   Allow destructive actions without   reviewing them  first .  Before any write or high - impact action  •   Confirm the AI is acting on the   correct project, file, issue or environment .  •   Clearly identify the   intended target and fields , and review them before the AI performs the update.  Example workflows  •   Figma →   design information assists frontend implementation.  •   Jira →   issue details retrieved as development context (updates only where permitted and reviewed).  Detailed reference:   MCP   Integration & Safe Usage

TatvaSoft   AI Development Tools Guidelines   TVS - DEV - AI - GL - 01 | v1.0 | 25.09.2026  TVS · Internal   Page   14   of   16  Data Privacy & Licensing  NO N   -   NE G O T I A B L E  These rules protect TatvaSoft and client data. They are   mandatory   for everyone using AI tools on project  work.  Strict Tool Configuration  •   Configure all approved AI tools with the   most restrictive security, privacy, data - retention and data - sharing  settings   approved by TatvaSoft and/or the client.  •   Where available, ensure code, prompts, files and other inputs are   not used for model training   or shared  beyond the authorised service scope.  No Unauthorised Setting Changes  •   Do   not   alter, downgrade, disable or bypass approved security, privacy, data - sharing, retention or access -  control settings.  •   Any change requires   prior formal approval   from the PM/PRM and, where applicable, the Information  Security team and/or client.  Strictly Prohibited Inputs  Never   submit, upload, paste or otherwise expose the following to AI tools   —   unless explicitly authorised under  an approved process:  ✘   Production secrets, passwords, API keys, tokens,  certificates or private keys  ✘   Customer / client confidential information  ✘   Personally identifiable information (PII) or other  personal data  ✘   Proprietary or commercially sensitive information  ✘   Production database content or live production  data  ✘   Database dumps, backups or production data  extracts  ✘   Confidential business documents or credentials  ✘   Any information restricted by contractual,  regulatory or client - specific requirements  When in doubt, don't submit it   —   confirm its classification and permitted usage first.  No Personal or Unapproved Accounts / Tools  •   Do   not   use personal accounts, free/personal - tier accounts or unapproved AI tools for any work involving  TatvaSoft or client information (development, testing, design, documentation, etc.).  •   Use   only company - approved accounts and AI tools   for project activities.  Data Minimisation  Share   only the minimum information necessary   for the task. Where practical:  •   Remove or anonymise sensitive information before submission.  •   Use representative or   synthetic data   instead of real data.  •   Share only the relevant code snippet / file   —   not the entire repository or project.  •   Remove secrets, credentials, tokens, comments containing confidential information and unnecessary  business logic.

Incident Response  •   Report immediately   —   through the applicable security/incident reporting process   —   any accidental  exposure of personal data, client data, proprietary information, credentials, secrets or other restricted  information to an AI tool.  •   Do   not   conceal, independently resolve or delay reporting an accidental exposure.  NO T E   —   C L I E N T R E QU I R E M E NT S C O M E FI R ST  Client - specific privacy and security requirements always take precedence over these guidelines. Where a  client contract, security policy, DPA, NDA or other documented requirement imposes   stricter   restrictions on  AI tool usage, the stricter requirement must be followed.
